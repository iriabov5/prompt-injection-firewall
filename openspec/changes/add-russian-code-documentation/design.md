## Context

См. `proposal.md` — Why. Проект уже содержит production-код в `src/main/kotlin` и тесты в `src/test/kotlin`; дальнейшая разработка идет этапами через OpenSpec, поэтому требования к документации должны применяться как к существующим файлам, так и к новому коду каждого следующего этапа.

## Goals / Non-Goals

**Goals:**

- Добавить русскую KDoc/Javadoc-документацию к существующим meaningful production declarations.
- Добавить русские JUnit 5 `@DisplayName` к существующим test classes и test methods.
- Зафиксировать правило, что новый production-код и новые тесты получают документацию сразу в том же change.
- Сохранить краткость: документация должна объяснять назначение, контракт, ограничения и важное поведение.

**Non-Goals:**

- Не менять бизнес-логику prompt analysis, scoring, HTTP API или Micronaut configuration.
- Не добавлять отдельный documentation generator или публикацию Dokka/Javadoc.
- Не писать комментарии для каждой строки, приватной переменной или очевидного getter-like поведения.

## Decisions

### Decision: Использовать KDoc/Javadoc над декларациями

Русские комментарии будут размещаться как KDoc/Javadoc над классами, интерфейсами, enum, data classes, публичными методами и важными внутренними методами, если они несут контракт или нетривиальное поведение. Альтернатива — писать отдельную документацию в Markdown, но она хуже видна в IDE и быстрее расходится с кодом.

### Decision: Делать `@DisplayName` обязательным для классов и сценариев тестов

Каждый test class и test method получит русское описание через JUnit 5 `@DisplayName`. Альтернатива — оставить человекочитаемые Kotlin method names в backticks, но Gradle/JUnit reports и IDE tree будут менее единообразны, особенно при смешении английских и русских названий.

### Decision: Документировать текущее состояние и future changes

Реализация change должна пройти по уже существующим файлам, а затем правило должно применяться к каждому следующему change. Альтернатива — ограничиться текущим cleanup, но тогда новое покрытие документацией начнет деградировать уже на следующем этапе.

## Risks / Trade-offs

- [Risk] Комментарии могут стать шумными и дублировать код → Mitigation: документировать назначение, контракт, ограничения, concurrency, validation и security-смысл, а очевидную механику не пересказывать.
- [Risk] Русские `@DisplayName` могут разойтись с именами тестов → Mitigation: считать `@DisplayName` основным человекочитаемым названием сценария и обновлять его вместе с тестом.
- [Risk] Изменение затронет много файлов без runtime behavior changes → Mitigation: коммит должен быть отдельным и сфокусированным только на документации и test display names.

## Migration Plan

1. Просмотреть `src/main/kotlin` и добавить недостающий русский KDoc/Javadoc.
2. Просмотреть `src/test/kotlin` и добавить русские `@DisplayName` для классов и методов.
3. Запустить тесты и OpenSpec validation.
4. В следующих этапах применять это как часть Definition of Done.
